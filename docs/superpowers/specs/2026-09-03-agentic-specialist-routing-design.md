# Agentic Specialist Routing and Order Cancellation Design

Date: 2026-09-03

Status: proposed, user review required

## Decision summary

The customer-support application will use one main supervisor workflow with a structured
intent classifier and task planner. The supervisor understands the incoming message, creates
one or more typed tasks, and routes each task to a reusable specialist subgraph.

The specialist set is:

- `OrderAgent`: order status, order ownership, fulfilment, payment state, cancellation assessment,
  and cancellation review preparation;
- `ProductAgent`: product, price, stock, recommendation, and offer lookups from bounded database
  tools;
- `ReturnRefundAgent`: return eligibility, refund implications, and review preparation for
  side-effecting actions;
- `RagAgent`: unstructured policy, service, FAQ, and general knowledge questions using the
  existing contextual hybrid RAG subgraph.

The main workflow remains responsible for conversation memory coordination, customer-facing
responses, task fan-out and join, durable case creation, and human-review delivery. A specialist
does not write directly to the UI or mutate an order. It returns a validated result to the main
workflow.

Cancellation is always assessed by `OrderAgent` and then handed to human review after the agent
has collected and verified the required order information. Automatic cancellation is out of scope
for this prototype.

## Problem and rationale

The current application presents static retail forms inside the client chat and uses keyword
branches in the main graph to call product and order tools. That does not provide a conversational
agent that can ask for missing information, remember the answer, investigate an order, or explain
why a request must be reviewed.

The target experience is a single client conversation. The customer can ask a natural-language
question about products, prices, offers, order status, cancellation, returns, or general policy.
The system decides which specialist work is needed. The customer does not select a workflow from
tabs or fill a task-specific form.

The design separates two types of truth:

1. Operational facts, such as order status, payment state, price, stock, and offers, come from
   scoped application tools and the synthetic operations database.
2. Unstructured explanations, such as cancellation policy or general support information, come
   from the contextual hybrid RAG subgraph and retain citations.

This prevents an LLM from inventing operational facts while preserving the existing RAG capability
for questions that are not answered by transactional tools.

## Goals

1. Route natural-language messages to one or more appropriate specialists.
2. Support compound messages by creating multiple tasks and joining their results.
3. Preserve the existing RAG subsystem as a reusable specialist path.
4. Give `OrderAgent` its own state, memory, tool loop, and clarification behavior.
5. Ask for a missing order number conversationally and resume the same specialist on the next
   message.
6. Search the database again after a corrected order number is supplied.
7. Return control to the main workflow after a terminal specialist result.
8. Produce a human-review packet containing verified order facts and policy findings before any
   cancellation action.
9. Keep policy enforcement deterministic and prevent model-selected database mutations.
10. Show one coherent client conversation while retaining a separate internal review workspace.

## Non-goals

- Automatic cancellation, refund, or other order mutation without human approval.
- Arbitrary SQL generated by a model.
- Static retail forms as the primary client interface.
- Replacing the contextual hybrid RAG subsystem with database tools.
- Treating an LLM explanation as proof of an order fact or policy decision.
- Production identity, payment processing, or real fulfilment integration.

## Target architecture

```text
Incoming chat or simulated email
              |
              v
      Main supervisor workflow
              |
              v
   Intent classifier and task planner
              |
       typed task plan with dependencies
              |
   +----------+-----------+----------------+------------------+
   |                      |                |                  |
   v                      v                v                  v
 OrderAgent          ProductAgent   ReturnRefundAgent      RagAgent
   |                      |                |                  |
   v                      v                v                  v
 typed result        typed result   typed result       cited result
   |                      |                |                  |
   +----------+-----------+----------------+------------------+
              v
          Join results
              |
              v
 Main workflow response or review handoff
              |
      +-------+--------+
      |                |
      v                v
 customer reply   durable human review
```

The main workflow is a supervisor and coordinator, not a second unrestricted general-purpose
agent. The classifier chooses from a closed set of intents. Conditional graph edges select
specialists. Specialists may use local LLM reasoning inside their own bounded state machine, but
their available tools, output schema, and side effects are controlled by application code.

## Classifier and task planner

### Classifier responsibility

The classifier understands the complete message, extracts entities, identifies all requested
tasks, and proposes dependencies. It does not answer the customer, call business tools, or approve
an external action.

The classifier output is validated against a Pydantic model conceptually equivalent to:

```text
RoutingDecision
  tasks: tuple[PlannedTask, ...]
  active_task_id: str | None
  clarification_required: bool
  clarification_reason: str | None
  classifier_model: str
  classifier_prompt_version: str
```

Each planned task contains:

```text
PlannedTask
  task_id
  intent
  user_text
  extracted_entities
  depends_on
  specialist
```

The closed intent set is:

- `product_search`;
- `product_recommendation`;
- `order_status`;
- `order_cancellation`;
- `return_or_refund`;
- `knowledge_question`;
- `clarification_required`;
- `unsupported`.

`order_status` and `order_cancellation` both route to `OrderAgent`. They are separate intents for
the planner and final response, but they share the same specialist because cancellation requires
the order lookup and inspection steps first.

### Hybrid routing policy

Routing uses two layers:

1. Deterministic hard gates detect mandatory review categories, external actions, malformed input,
   and active specialist state. These rules cannot be downgraded by the model.
2. The local classifier handles semantic intent understanding, entity extraction, and multi-intent
   decomposition when no hard gate has already fixed the safety outcome.

The classifier may add a review requirement, but it cannot clear a deterministic review decision.
Classifier failures produce a safe clarification or service-failure result, never an automatic
business action.

### Compound messages

The planner supports multiple tasks. For example:

> “Has order ORD-1001 shipped, can you cancel it if it has not, and what is your refund policy?”

becomes:

1. `order_cancellation`, handled by `OrderAgent`, with status inspection as an internal dependency;
2. `knowledge_question`, handled by `RagAgent`.

Independent tasks can fan out in one LangGraph superstep. Dependencies are respected before a task
starts. The order agent does not expose its internal status lookup as a separate customer task when
the user asked for cancellation. It performs the required investigation internally, then returns
one cancellation result.

## Specialist contract and handoff

Every specialist is compiled as a reusable graph with an explicit input and output contract.

The main workflow passes:

```text
conversation_id
client_id
current_message
active specialist state reference
planned task
safe conversation context
```

The specialist returns a typed `SpecialistResult` containing:

```text
specialist
task_id
status
customer_message_or_message_intent
facts
citations
review_packet
missing_information
events
```

The `customer_message_or_message_intent` field is not an instruction to write directly to the
client. The main workflow chooses the final wording and combines results from multiple specialists.

Terminal statuses include:

- `needs_information`;
- `correction_requested`;
- `completed`;
- `review_required`;
- `not_found`;
- `unsupported`;
- `tool_unavailable`;
- `failed`.

The main workflow persists the result and clears or updates the active specialist state according
to the terminal status.

## OrderAgent

### Responsibility

`OrderAgent` handles both informational order requests and cancellation requests. It owns the
order investigation sequence, not the customer-facing channel and not the final review persistence.

It uses bounded typed tools for:

- customer-scoped order lookup;
- order item and fulfilment inspection;
- payment-state inspection without exposing payment references;
- cancellation eligibility and policy evaluation;
- creation of a side-effect-free cancellation proposal.

There is no cancellation execution tool available to the automatic agent path.

### State and memory

The agent state is keyed by `conversation_id` and isolated by `client_id`. It includes:

```text
OrderAgentState
  conversation_id
  client_id
  task_id
  requested_operation
  order_id
  order_lookup_attempts
  last_submitted_order_id
  order_found
  verified_order_summary
  payment_summary
  fulfilment_summary
  cancellation_checks
  policy_findings
  missing_information
  review_packet
  phase
  last_result
```

Conversation memory is durable application state or a checkpointer-backed specialist state keyed
by the conversation thread. It is separate from the human-review queue. The review queue remains
the source of truth for cases, review decisions, and delivery; specialist memory records the
unfinished conversational investigation.

The state must not retain card numbers, authentication secrets, or unrestricted payment references.

### Nodes and transitions

The initial specialist graph contains these explicit nodes:

1. `understand_order_request`: validate the planned intent and determine whether status,
   cancellation, or both are required.
2. `collect_order_id`: use the stored entity if valid; otherwise return `needs_information` so the
   main workflow asks the customer for the order number.
3. `lookup_order`: call the scoped order tool and record the attempt and result.
4. `inspect_order`: when found, collect status, items, fulfilment, payment state, total, and any
   facts needed for the requested operation.
5. `evaluate_cancellation_policy`: for cancellation requests, run deterministic policy checks and
   record each pass, failure, exception, or missing fact.
6. `prepare_cancellation_review`: create a side-effect-free review packet containing the verified
   order summary and policy findings.
7. `return_to_main_workflow`: return a typed result and specialist events to the supervisor.

The lookup correction state machine is:

```text
No order ID
  -> NEEDS_INFORMATION
  -> main workflow asks for order number

First lookup miss
  -> CORRECTION_REQUESTED
  -> main workflow asks the customer to review the number

Second lookup miss
  -> NOT_FOUND
  -> main workflow says there is no information related to that order number
  -> order task ends, no cancellation review is created

Lookup succeeds
  -> inspect order
  -> status result, or cancellation policy evaluation
  -> cancellation review packet
  -> main workflow
```

The corrected order number is routed back to the active `OrderAgent` state. The main workflow does
not start a new generic task or require the user to repeat the original cancellation request.

### Cancellation review packet

After all required facts are collected, the agent returns `CANCELLATION_REVIEW_READY` with:

```text
CancellationReviewPacket
  conversation_id
  client_id
  original_request
  order_id
  customer-scoped order summary
  items and quantities
  current order status
  fulfilment and shipment state
  payment state and refund implication
  cancellation policy checks
  policy issues and exceptions
  missing or conflicting facts
  recommended reviewer action
  tool and policy provenance
```

The main workflow persists one case and one review request. The customer receives an acknowledgement
that the cancellation is awaiting review. The system must never claim that the order was cancelled
until a reviewer approves the action and the approved application command succeeds.

If the order is not found, the packet is not created because there are no verified facts to summarize.
An order belonging to a different customer is returned as not found to avoid disclosing its existence.

## ProductAgent

`ProductAgent` handles product search, recommendation, price, stock, and offer questions using
read-only typed database tools. It returns exact product facts and does not invent missing prices,
offers, or inventory.

Recommendations may use the local model to interpret preferences, but product facts remain sourced
from the database. If the user asks an additional policy question in the same message, that becomes
a separate `knowledge_question` task for `RagAgent`.

## ReturnRefundAgent

`ReturnRefundAgent` handles return and refund requests. It gathers order and item facts, evaluates
eligibility, records risk flags and policy findings, and produces a side-effect-free proposal.
Financial, irreversible, late, disputed, duplicate, or otherwise exceptional operations return to
the main workflow as human-review work. The agent has no automatic refund execution capability.

## RagAgent and the existing RAG subsystem

The existing contextual hybrid RAG graph remains a reusable specialist. It continues to perform:

1. query preparation;
2. dense and lexical retrieval;
3. evidence selection and conflict detection;
4. cited answer generation when evidence is sufficient.

RAG handles unstructured questions such as:

- “What is the cancellation policy?”;
- “How do returns work?”;
- “What services do you provide?”;
- “Why is my refund still pending?” when the answer requires policy or process explanation.

RAG does not supply order status, prices, stock, payment state, or cancellation authorization. Those
facts come from the appropriate operational specialist. Sensitive or action-oriented requests may
use RAG in evidence-only mode for the reviewer packet, but the RAG model must not draft the customer
response for a mandatory-review case.

## Multi-task join and customer response

The main workflow uses dependency-aware fan-out and a reducer-based join. Results remain keyed by
`task_id`, so citations, operational facts, and review packets cannot overwrite one another.

For a compound message containing safe information and an external action:

- the safe RAG or product result is prepared for the customer immediately;
- the cancellation or refund result is represented as pending human review;
- the final response clearly separates verified information from the pending action;
- no pending action is described as completed.

For example, a joined response can explain the refund policy with citations, report the verified
order status, and state that cancellation has been submitted for human review.

## Human-review handoff

The main workflow receives `review_required` from a specialist and performs the application-level
transaction that creates or reuses the case and review request. The specialist does not create
duplicate cases or outbox rows.

The reviewer sees:

- the original customer request;
- the verified order summary;
- the tool results and timestamps needed for audit;
- the policy checks and issues against the configured prototype policy;
- the proposed action;
- missing, conflicting, or unavailable information;
- any permitted RAG evidence and citations.

Reviewer decisions are approve, reject, request information, or take ownership. Approval is the
only path that may authorize a cancellation command. The command is idempotent and uses optimistic
version checks. Delivery through the simulated mailbox occurs only after the business mutation and
review decision are durably committed.

## Error and safety behavior

- Missing order identifiers produce a clarification request, not a database query with guessed data.
- Invalid or unknown order identifiers follow the two-lookup correction policy above.
- Customer scoping is enforced inside the tool, not by the model prompt.
- Tool timeouts and unavailable dependencies return explicit failure results.
- Classifier uncertainty cannot authorize an action.
- Policy evaluation is deterministic and records its version and findings.
- Prompt-injection-shaped content is treated as untrusted user data.
- Tool outputs are validated before they enter specialist state or review packets.
- Payment data is minimized and never exposed to the customer.
- A reviewer packet is immutable after creation except through versioned reviewer decisions.

## Observability

Every message and specialist task records:

- correlation ID, conversation ID, task ID, and specialist name;
- classifier decision and prompt/model versions;
- specialist node events and durations;
- tool name, bounded operation, success state, and safe summary;
- lookup attempt number and terminal outcome;
- RAG retrieval status, selected evidence count, and citation markers;
- review case ID, queue time, decision, and delivery status.

The UI exposes operational trace information, not hidden chain-of-thought. The client sees the
conversation, safe status, citations, and review acknowledgement. The reviewer sees the order and
policy summary needed for a decision.

## Client interface

The client view is one conversational screen with a natural-language chat input. Suggested examples
may be displayed as plain text, such as:

- “Do you have a waterproof jacket, and what is the current offer?”
- “What is the status of order ORD-1001?”
- “I want to cancel my order.”
- “What is your refund policy?”

Examples must submit through the same chat path as typed messages. They must not be implemented as
separate product, recommendation, order, or return forms.

Simulated email remains a second channel using the same main workflow. Human review remains an
internal workspace and is not presented as a client route selector.

## Testing and acceptance criteria

The implementation is complete only when the following behaviors are covered by focused tests and
live UI checks:

1. A product price or offer question routes to `ProductAgent` and returns database facts.
2. A general policy question routes to `RagAgent` and returns citations.
3. A compound product or policy plus order-cancellation message creates multiple tasks and joins
   their results.
4. A cancellation request without an order number asks for it in the same conversation.
5. A first order lookup miss asks the customer to check the order number.
6. A second lookup miss returns the final no-information response through the main workflow and
   creates no review case.
7. A corrected order number resumes the active `OrderAgent` without losing the cancellation intent.
8. A found order produces verified status, payment, fulfilment, amount, and policy findings.
9. A completed cancellation investigation creates exactly one human-review packet and no order
   mutation.
10. Reviewer approval is required before cancellation execution, and duplicate approval is idempotent.
11. An order belonging to another customer is not disclosed.
12. Tool failures, classifier failures, insufficient RAG evidence, and conflicting evidence produce
    explicit safe outcomes.
13. The client UI contains one chat input and no static retail task forms.
14. The UI displays specialist routing, tool activity, citations, and review status without exposing
    private model reasoning.

## Migration boundary

The existing RAG ingestion, retrieval, citation, mailbox, asynchronous review, and bounded database
repositories remain in scope for reuse. The implementation will replace the current retail keyword
branches and static retail workspace with the classifier, specialist contracts, OrderAgent state,
and supervisor routing described here.

The implementation plan must keep the work phase-bounded. It should first establish the contracts
and routing path, then implement OrderAgent memory and tool loops, then integrate ProductAgent,
ReturnRefundAgent, and RAG task joining, and finally remove the static client forms and run the
end-to-end UI checks.
